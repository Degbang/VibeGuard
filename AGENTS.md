## 2. What VibeGuard Is

A five-layer explainable security assessment framework for Java microservices generated by AI coding tools (Copilot, Cursor, ChatGPT, Bolt, etc.). It detects, scores, and explains vulnerabilities across five CWE categories, using a hybrid of rule-based detection and machine learning, with SHAP-based explainability so results are interpretable, not a black-box score.

**Do not conflate these two things** (a documented point of confusion to avoid):
- SHAP explains **feature-level attribution** — why the ML model scored something the way it did.
- Layer 1 (AST parsing) provides **file/line traceability** — where in the source the issue physically is.
These serve different purposes and both must be present in final output.

## 4. Coding Standards (apply to every file, every layer)

### Structure & typing
- Full type hints on every function signature and every class attribute.
- Use `@dataclass` (or `pydantic` models if validation logic grows complex) for structured data — never raw dicts passed between modules.
- One responsibility per function. If a function needs "and" in its description, split it.
- No function should exceed ~40-50 lines as a soft ceiling; if it does, it's a signal to decompose.

### Documentation
- Docstrings on every public function, class, and module — Google-style docstrings, applied consistently across the whole codebase.
- Every module starts with a short module-level docstring stating its role in the five-layer pipeline.

### Style & tooling
- PEP 8 compliant.
- **Formatter:** `black`, run before every commit.
- **Linter:** `ruff` (covers flake8-equivalent checks faster). Zero lint warnings in committed code.
- **Type checker:** `mypy` in strict-ish mode (`disallow_untyped_defs = true` at minimum) — this is a security tool; type errors are bugs waiting to happen.
- Add all three to `requirements.txt` / `pyproject.toml` from the very first commit, not retrofitted later.

### Logging & errors
- Use Python's `logging` module. Never `print()` for anything other than final user-facing CLI/report output.
- Fail closed, never silently: a file that can't be parsed, scored, or classified must be explicitly flagged in output (`parse_failed`, `scoring_failed`, etc.), never dropped from results without a trace. Silent failures in a security tool under-report vulnerabilities, which is a correctness bug, not a cosmetic one.

### Testing
- `pytest` for everything. Every layer gets its own `tests/` coverage before being considered "done."
- Maintain fixture Java files under a dedicated `tests/fixtures/` directory: at minimum, one clean file, one file per target CWE with a known instance of that vulnerability, one malformed/unparseable file, one empty file.
- Target meaningful coverage on detection logic specifically (rule modules, scorer, ML pipeline) — coverage on glue code matters less than coverage on the parts making security judgments.

## 5. Security Requirements (this tool analyses untrusted, AI-generated code)

- **Never execute or `eval()` any content from a target Java file.** VibeGuard only ever parses text into an AST — it must never run the code it's analysing. State this explicitly in a comment in `scanner.py` and in the thesis, since a reviewer will ask.
- Guard against path traversal: resolve all file paths with `Path.resolve()` and verify they remain inside the expected sample-apps root before reading.
- Set limits on input size and parse time per file (a large or adversarial file must not hang or OOM the process) — this is also a legitimate "robustness" evaluation point for Chapter 4/5.
- No secrets, API keys, or credentials — real or plausible-looking — committed anywhere outside clearly labeled test fixtures.
- Dependency hygiene: pin versions in `requirements.txt`, and periodically check for known-vulnerable dependencies with `safety check`. **As of the 2026-10-02 re-run, the audit is clean**: 0 vulnerabilities across the full installed environment. This was not always true — the 2026-09-10 QA re-run found 2 CVEs (one in `pip` itself, one in `cryptography`, both pulled in transitively by `safety`'s own dependency chain, not by anything VibeGuard's own code imports) with no upgrade path available at the time. A later re-run found upgraded `nltk`/`cryptography` releases (both also transitive, via `safety`'s own chain, specifically `nltk>=3.9` and Authlib/joserfc's `cryptography` pin) that clear every then-open finding. Re-verify before citing a specific count in Chapter 5 — this list has changed direction more than once already as upstream packages shipped fixes, and should be treated as a snapshot at time of writing, not a permanent claim.

## 8. Layer Completion Discipline — mandatory prompt for every task

Before starting any implementation, review this section and apply it to
the current layer/module. The goal is to finish one scope cleanly, log
it, freeze it, and move forward — not repeatedly reopen earlier work
without a blocking reason.

Use this prompt at the start of every VibeGuard coding session:

```text
You are working on VibeGuard, a five-layer Master's thesis security
tool. Work as a strict, security-conscious QA/implementation engineer.
Do not optimize for reassurance. Optimize for finishing the current
layer/module to a defensible standard, documenting it, and moving on.

For the current task:

1. Define the exact scope before editing.
   - Name the layer/module being worked on.
   - State what is in scope.
   - State what is explicitly out of scope.

2. Implement only that scope.
   - Keep changes minimal and modular.
   - Preserve existing behavior unless the scoped task requires a change.
   - Do not drift into adjacent layers or speculative refactors.

3. Test aggressively before declaring the scope done.
   - Run normal unit tests.
   - Run static gates: mypy, ruff, black --check, git diff --check.
   - Run adversarial QA relevant to this scope: malformed input, empty
     input, edge-case syntax/data, duplicates, missing values, huge values,
     Unicode/encoding cases, traceability/line-number checks, and any
     fail-closed behavior required by the project.

4. Fix only issues found inside the current scope.
   - If testing reveals a real bug in the current layer/module, fix it and
     add a regression test.
   - If testing reveals a broader design issue outside the current scope,
     log it as a limitation or future task instead of derailing the layer.

5. Log the implementation.
   - Add an IMPLEMENTATION_LOG.md entry explaining:
     - what the plan/scope was;
     - what was actually implemented;
     - what tests/adversarial checks were run;
     - what limitations remain;
     - what this means for thesis Chapters 3/4/5.

6. Freeze the scope.
   - Once tests pass and the implementation is logged, mark the
     layer/module as frozen in the working summary.
   - Do not reopen frozen work unless a later layer exposes a blocking
     correctness issue.

7. Move forward.
   - The next response after a freeze should identify the next layer/module
     and repeat this same discipline.
```

Current freeze status must be respected:

- Layer 3 deterministic rule-based scoring is frozen unless Layer 4

If a user asks to "test more" or "try to break it" after a layer is
